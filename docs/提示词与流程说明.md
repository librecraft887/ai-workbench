# 培训需求、客户调研与方案写作规范

本次优化落实用户已明确的顺序：先互动提问、再围绕培训需求调研、最后设计配课。系统采用三个独立请求，避免课表提前生成或调研仅作为附件补充。

## 需求澄清

提取客户名称、培训对象、主题、天数、课次、培养目标、业务问题、学员基础和实施偏好。结合助手追问理解用户的简短补充，用户最近一次明确修改优先。用户未接受的助手建议不计入已确认需求。

关键内容不足时返回 clarify：先概括已有信息，再只询问缺失内容，并给出培养目标的表达示例。用户可委托方案建议目标，系统明确标为待客户确认；可不提供客户名称，系统按用户需求设计。

## 调研

调研提示词由 edge-functions/api/chat.js 中 buildResearchPrompt 生成。输入包括已明确的培养目标、业务问题、培训主题、对象及学员基础。检索客户相关战略、业务发展和人才培养举措，筛选最影响本次培训的2—3条背景线索，提出能关联课程模块和教学方式的设计启示。

来源事实、需求与方案建议按不同口径使用。主检索来源须有联网响应引用支撑；备用检索摘要保留为线索，未经原文核验不称为官方结论。

## 三段分析与配课

实际写作提示词在 edge-functions/lib/proposal.js 的 proposalPrompt 中，与正式课程候选一起传入模型。

“项目背景”：综合与主题相关的战略、业务和人才线索，解释为什么开展项目。建议150—250字，体现对客户工作场景的理解。关联编号仅保存在内部source_ids字段，客户正文不标注来源。

“客户需求分析”：以已确认目标和岗位特征为基础，分析重点发展的2—3类能力，连接业务背景、岗位应用与学习需求。建议150—250字；直接使用“本项目聚焦”“课程重点回应”等方案表达，不出现检索口径，不虚构内部短板。

“方案设计逻辑”：以模块设计依据、模块关系与整体学习路径为主，解释组合理由、教学方式及学习成果。建议200—350字，按逻辑分为两段，自然过渡到配课。无需逐门展开，可选1—2门实际课程作为补充。内部师资来源、资格过滤与测试关系不写入客户方案。

三段为连贯分析并适当分段，正文首行缩进两字符。每行课程适当补充学习重点和能力目标。师资课程组合与内部来源关联由服务端核验，正文不介绍这一处理过程。培训概览补全培养目标、教学方式和预期学习成果，未确认的执行事实不填造。

资料不足时只基于需求形成正文；模型方案缺失、内部来源编号无效或课程组合未通过校验时采用保守回退。页面、复制文本、Word 共用同一方案正文；原始摘要与来源仅保留为页面内部参考，不导出到客户文件。课程行有真实备注或已关联资料链接时才显示“查看依据”，占位备注直接忽略。
